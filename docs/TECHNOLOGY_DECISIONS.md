# 카툰플러스 기술 도입 의사결정서

**상태:** 승인된 MVP 기준  
**마지막 검토:** 2026-09-07  
**적용 범위:** 고객용 웹, 직원용 관리 화면, 빌드·배포, 개발·문서 관리 방식

## 1. 의사결정의 기준

카툰플러스는 만화카페 고객의 빠른 도서 탐색과 매장 직원의 재고·입고 신청·안내 방송 업무를 지원한다. MVP의 기술 선택은 다음 기준을 우선한다.

1. 월 고정 운영비를 0원으로 유지한다.
2. 모바일 고객 화면과 데스크톱 POS 화면을 빠르게 개선한다.
3. 도서 재고와 입고 신청을 지점별로 정확하게 관리할 수 있어야 한다.
4. 한글 공백 무시·초성 검색과 한국어 TTS를 브라우저에서 가볍게 제공한다.
5. MVP 검증 후 실제 데이터·인증 기반으로 확장할 수 있어야 한다.

## 3. 배포: GitHub Pages와 GitHub Actions

### 선택 이유

MVP 화면은 React로 생성한 정적 파일만으로 제공할 수 있다. GitHub Pages는 정적 파일 호스팅을 제공하므로 별도 서버를 운영하지 않아도 되고, GitHub Actions는 `main` 브랜치 변경 시 테스트와 빌드를 거쳐 배포할 수 있다. 이 조합은 초기 운영비를 줄이면서 배포 절차를 반복 가능하게 만든다.

Vite 설정의 상대 경로(`base: './'`)와 HashRouter는 GitHub Pages의 하위 경로 및 새로고침 시 SPA 경로를 안정적으로 처리하기 위해 사용한다.

### 대안과 판단

| 대안 | 판단 |
| --- | --- |
| Vercel | 서버 기능이나 프리뷰 환경이 필요해질 때 검토한다. 현재 정적 MVP에는 GitHub Pages로 충분하다. |
| 자체 서버 | 운영·보안·배포 관리 비용이 증가하므로 MVP 기준에 맞지 않는다. |
| 수동 파일 업로드 | 배포 누락과 사람 의존을 늘리므로 사용하지 않는다. |

### 한계와 운영 결정

GitHub Pages는 서버 API, 비밀키 보관, 서버 측 인증을 제공하지 않는다. 따라서 실제 개인정보·직원 인증·공유 데이터가 필요한 기능은 Supabase와 연결하되, 브라우저에는 공개 가능한 환경 변수만 둔다.

현재 `.github/workflows/`에는 빌드 결과물 `dist`를 배포하는 `deploy.yml`과 저장소 전체를 배포하는 `static.yml`이 함께 있다. 표준 워크플로는 **테스트와 빌드 후 `dist`만 배포하는 방식**으로 확정해야 하며, `static.yml`의 유지·삭제는 다음 설정 관리 작업에서 결정한다.

## 4. 프론트엔드 기술 스택

### React

React는 지점 선택, 검색어·장르 필터, 도서 입고 신청 모달, 로그인 상태, 방송 재생 상태처럼 화면의 상태가 많은 서비스를 관리하기 위해 선택했다. 같은 도서 카드, 헤더, 모달, 관리자 표를 컴포넌트로 분리하면 고객 화면과 직원 화면의 수정 범위를 줄일 수 있다.

또한 Supabase 연동 시 데이터 조회와 갱신 결과를 화면 상태에 연결하기 쉬워 MVP의 Mock 데이터 구조에서 실제 데이터 구조로 전환하기에 적합하다.

### Vite

Vite는 React 프로젝트의 개발 서버와 프로덕션 번들을 담당한다. 개발 중 화면·스타일 변경을 빠르게 확인할 수 있고, 결과물을 정적 파일로 생성하므로 GitHub Pages 배포 방식과 바로 연결된다.

Next.js처럼 서버 렌더링 중심의 프레임워크는 현재 정적 호스팅과 브라우저 기반 검색·TTS 요구에 비해 운영 구조가 무거워 MVP에서 채택하지 않았다. 서버 렌더링, SEO 중심 콘텐츠 운영, 서버 API가 제품의 핵심이 되면 재검토한다.

### TypeScript

TypeScript는 `Book`, `BookInventory`, `BookRequest`, `Store`처럼 서로 연결된 데이터를 다룰 때 필드 누락과 타입 불일치를 빌드 전에 발견하기 위해 사용한다. 특히 도서명·권수·서가 위치를 분리하고 지점별 재고를 연결하는 데이터 모델에서 오류를 줄인다.

### Tailwind CSS

Tailwind CSS는 화면 가까이에서 반응형 규칙과 브랜드 토큰을 함께 관리하기 위해 선택했다. 카툰플러스의 시그니처 옐로우와 차콜 색상, 고객용 모바일 화면, 직원용 POS 화면을 일관된 규칙으로 구현할 수 있다.

별도의 대형 컴포넌트 라이브러리를 기본으로 채택하지 않은 이유는 MVP의 브랜드 화면을 직접 조정해야 하고, 필요한 UI가 한정되어 있기 때문이다. 접근성·복잡한 입력 컴포넌트가 반복적으로 필요해지면 검증된 접근성 기반 컴포넌트 도입을 별도 결정한다.

고객 홈은 와이어프레임의 시그니처 옐로우·차콜·둥근 카드 분위기를 유지한다. 기능 조작에는 하나의 선형 SVG 아이콘 체계를 사용하며, 이모지·3D 스티커·생성형 장식 아이콘을 사용하지 않는다. 로고·마스코트·매장 사진은 실제 브랜드 자산과 사용 허가된 체험단 사진으로만 구성한다. 도서 검색과 직원 화면에서는 장식보다 정보 가독성을 우선한다.

### React Router

React Router는 홈, 검색, 즐길거리, 메뉴, 매장 안내, 직원 콘솔을 각 경로로 나누고 URL 기반 탐색을 제공한다. 직원 콘솔은 인증 상태에 따라 접근을 제어하는 경계가 필요하므로 별도 경로로 관리한다.

### Lucide React, clsx, tailwind-merge

Lucide React는 UI 의미를 보완하는 일관된 아이콘을 제공한다. `clsx`와 `tailwind-merge`는 상태에 따라 Tailwind 클래스를 조합하면서 충돌을 정리한다. 세 도구는 공통 UI 구현을 간결하게 유지하지만, 제품의 핵심 로직을 대신하지는 않는다.

### Vitest와 Testing Library

Vitest는 Vite 프로젝트와 같은 도구 체계를 사용해 빠르게 테스트를 실행한다. Testing Library는 사용자가 보는 결과를 기준으로 화면 흐름을 검증하는 데 사용한다. 우선 검증 대상은 공백 무시·초성 검색, CSV/XLSX 가져오기, 인증 경계, TTS 상태 변화다.

## 5. Supabase: 실제 운영 데이터와 인증을 위한 다음 단계

### 도입 이유

현재 MVP는 브라우저의 Mock 데이터와 `localStorage`를 사용한다. 이 방식은 화면과 검색 경험을 빠르게 검증하기에는 좋지만, 손님이 휴대폰에서 제출한 입고 신청을 직원 POS에서 볼 수 없고, 지점별 재고를 여러 기기에서 동기화할 수 없다.

Supabase는 PostgreSQL 데이터베이스, 인증, 행 단위 보안 정책을 제공하므로 다음 문제를 하나의 관리 지점에서 해결할 수 있다.

- `stores`, `books`, `book_inventories`, `book_requests`를 관계형 데이터로 관리한다.
- 지점별 재고와 입고 신청을 여러 기기에서 동일하게 조회·수정한다.
- STAFF와 ADMIN 권한에 따라 재고 수정, 신청 처리, 운영 설정 접근을 구분한다.
- 프론트엔드에서 사용할 수 있는 JavaScript 클라이언트를 제공해 React 구조와 자연스럽게 연결한다.
- 초기 데이터 규모와 MVP 트래픽에 무료 티어가 적합해 운영비 0원 목표를 유지한다.

### 대안과 판단

| 대안 | 판단 |
| --- | --- |
| `localStorage` 유지 | 단일 브라우저 검증에는 적합하지만 다기기 데이터 공유와 실제 운영에 부적합하다. |
| 자체 API + 별도 PostgreSQL | 유연성은 높지만 서버·배포·보안 운영 비용이 MVP에 과하다. |
| Firebase | 실시간 문서형 데이터에는 강점이 있으나, 지점·도서·재고·입고 신청의 관계와 SQL 조회 요구에는 PostgreSQL 모델이 더 자연스럽다. |

### 도입 범위와 전제

Supabase는 아직 프로젝트에 연결되지 않은 **도입 예정 기술**이다. 도입 전에는 `docs/DATA_MODEL.md`를 기준으로 스키마, `(store_id, book_id)` 중복 방지, 소프트 삭제, 입고 신청 상태 전이, STAFF/ADMIN 권한 정책을 확정한다. 실제 인증 전환 전까지 현재 로컬 인증은 개발용이며 운영 인증으로 간주하지 않는다.

## 6. Codex 에이전트 사용

Codex는 제품 런타임에 포함되는 기술이 아니라 프로젝트 운영 도구다. 이 세션에서는 10년차 시니어 PM 관점에서 기획서, 요구사항 명세서, 데이터 모델, 기능 명세, 설정 현황, 트러블슈팅 기록을 연결한다.

### 사용하는 이유

- 요구사항, ADR, 코드, 테스트, 이슈 티켓 사이의 불일치를 조기에 찾는다.
- 기술 도입과 로직 선택의 근거·대안·영향을 문서로 남긴다.
- 구현 전 완료 기준을 구체화하고, 구현 후 검증 결과와 남은 위험을 기록한다.
- 반복되는 장애 원인과 해결 방법을 `docs/TROUBLESHOOTING.md`에 축적한다.

### 사람과 Codex의 역할

| 역할 | 책임 |
| --- | --- |
| 제품 책임자 | 제품 목표, 우선순위, 예산, 정책, 기술 선택의 최종 결정을 내린다. |
| Codex | 현황 조사, 선택지와 근거 정리, 문서 초안, 영향 분석, 검증과 기록을 수행한다. |

기술·로직·데이터 모델의 선택이 필요한 작업에서는 Codex가 후보, 근거, 비용과 영향, 권장안을 먼저 제시하고 제품 책임자와 문답으로 결정한다. 결정된 내용은 이 문서 또는 관련 ADR에 기록한다.
